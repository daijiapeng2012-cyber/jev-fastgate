WHY FASTGATE

不是换模型，而是重新分配“谁来判断”。

很多 Agent 工作流都在反复让通用大模型回答非常窄的问题：该走哪个分支？证据够不够？风险高不高？是否需要复核？FastGate 把这些问题变成结构化判断，把昂贵的深度推理留给真正困难的部分。

Route · 路由

在执行前，先决定走规则、Jev、Codex 深度推理还是人工复核。

Score · 评分

对风险、质量、准备度、证据充分性等放入明确的有序尺度。

Verify · 验证

在任务结束前，对验收条件做一次独立的快速判断，但不替代真正的测试和 Review。

WORKFLOW

Jev 是“门”，Codex 才是“司机”。

顺序很重要：能写死的规则先写死；规则解决不了但问题足够封闭时交给 Jev；开放式推理、代码、架构和调试仍由 Codex 完成；最后再由测试、Reviewer 或人工做真正的放行。

1 · 确定性规则能用 if / schema / test 解决的，不调用模型。
2 · JEV FastGate分类、评分、判断、匹配、筛选。
3 · Codex推理、研究、写代码、调试、执行。
4 · JEV 再检查独立判断完成度、风险和证据。
5 · 正式 Gate测试、Reviewer、人工批准、部署策略。
INSTALL

三步装好。

API Key 只放在你自己的环境变量里。安装脚本不会把 Key 写入 Skill、GitHub 或 Codex 配置文件。

本机设置 Jev API Key

Terminal 
export TYPESAFE_API_KEY="your_key_here"

运行安装 + 验证

Terminal 
chmod +x scripts/*.sh
./scripts/install.sh
./scripts/verify.sh

重启 Codex，加载 Skill

Codex 
/mcp
$jev-fastgate
建议第一阶段使用 Shadow Mode：让 Jev 判断、记录，但暂时不改变实际执行结果。积累真实数据后，再逐步开放低风险自动路由。

CODEX CONFIG

公开版安全配置。

这里使用 Codex 官方支持的 env_vars 转发环境变量，因此分享配置时不需要把 API Key 写进去。

~/.codex/config.toml 
# JEV FastGate — Codex MCP configuration
# Safe public template: no API key is stored here.
#
# Put the API key in your shell:
#   export TYPESAFE_API_KEY="..."
#
# Codex forwards the environment variable to the MCP process.

[mcp_servers.jev]
command = "uvx"
args = [
  "--from",
  "git+https://github.com/blakestone-x/jev-mcp@v0.2.1",
  "jev-mcp"
]
env_vars = ["TYPESAFE_API_KEY"]
enabled = true
SECURITY

可以分享，但不能把 Jev 当安全边界。

不包含 API Key

资料包只包含变量名 TYPESAFE_API_KEY，没有真实凭证。

置信度不是正确率

Jev 的结果是一个判断信号，不是“事实证明”，不能跳过测试和代码审查。

失败自动回退

429、超时、低置信度、结果冲突或高风险动作，都应该回退到 Codex / Reviewer。
